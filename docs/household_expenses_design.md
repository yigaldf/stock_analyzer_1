# תכנון כללי — אפליקציית הוצאות הבית

מסמך תכנון (design) לפני הפלן. מגדיר מה האפליקציה עושה, באיזה סטאק, ואיפה
נשמרים הנתונים. אין כאן קוד — הפירוט לאבני דרך ומשימות מגיע בשלב הפלן.

---

## 1. מה האפליקציה עושה

**קלט:** הקבצים שהמשתמש מוריד מהאתרים של הבנק ושל חברת האשראי. הפורמטים
המדויקים, שנבדקו מול קבצים אמיתיים, מפורטים בסעיף 16.

- **קובץ כרטיס אשראי** — `xlsx` עם פירוט העסקאות, כולל קטגוריה שחברת האשראי
  כבר נתנה, סימון תשלומים, וסימון **הוראת קבע**. זהו מקור האמת גם לחשבונות
  החשמל, המים והארנונה — הם משולמים בכרטיס, לא ישירות מהבנק.
- **קובץ תנועות חשבון** — **`PDF`**, לא Excel. כולל **שורת החיוב המרוכזת של
  האשראי**, ולצידה מה שלא עובר בכרטיס: משכנתא, ליסינג, ביטוחים, קופות והכנסות.

**פלט:**

1. כל הוצאות הבית **פר חודש**.
2. הפרדה בין **הוצאות קבועות חוזרות** (חשמל, מים, ארנונה, משכנתא, ביטוח, גנים)
   לבין הוצאות משתנות.
3. **סה"כ הוצאות לחודש** ו**ממוצע חודשי**.

**גנריות:** אין נתונים קשיחים של משפחה מסוימת. כל משפחה מייבאת את הקבצים שלה,
מגדירה את הקטגוריות וההוצאות הקבועות שלה, ומקבלת את התמונה שלה.

**לא בסקופ v1:** חיבור ישיר ל‑API של בנקים (Open Banking), ניהול השקעות,
תכנון תקציב עתידי, אפליקציית מובייל.

## 2. סטאק טכנולוגי

הממשק הוא חזית **React אמיתית**, לא כלי דשבורד. הסיבה: טבלת עסקאות עם אלפי
שורות ועריכה בתוך השורה, גרירת קבצים עם התקדמות, מצב כהה, קיצורי מקלדת,
שליטה מלאה ב‑RTL וגרפים עם hover — כל אלה נלחמים ב‑Streamlit ומגיעים בחינם ב‑React.

### חזית

| רכיב | בחירה | נימוק |
|---|---|---|
| מסגרת | **React 19 + TypeScript + Vite** | SPA מהיר, בלי SSR שאין בו צורך באפליקציה פרטית |
| עיצוב | **Tailwind CSS v4** + **shadcn/ui** (Radix) | רכיבים נגישים, תמיכת RTL בתכונות לוגיות, מצב כהה מובנה |
| מצב שרת | **TanStack Query** | קאשינג, invalidation, עדכון אופטימי |
| טבלה | **TanStack Table** + וירטואליזציה | 10k+ שורות בלי גמגום, עריכה בתוך התא |
| גרפים | **Recharts** | ראה מפרט הגרפים בסעיף 11 |
| טפסים | React Hook Form + Zod | ולידציה משותפת עם טיפוסי ה‑API |
| העלאה | react-dropzone | גרירה, התקדמות, ריבוי קבצים |
| שפה | i18next, עברית ברירת מחדל | RTL מהיסוד, אנגלית בהמשך |
| טיפוסים | openapi-typescript | טיפוסי TS נוצרים מ‑OpenAPI — החזית לא יכולה לסטות מהשרת |

### שרת

| רכיב | בחירה | נימוק |
|---|---|---|
| API | **FastAPI** async | תואם ל‑CLAUDE.md, OpenAPI אוטומטי |
| ולידציה | Pydantic v2 | חוזה אחד לשרת ולחזית |
| DB | SQLAlchemy 2.0 async + aiosqlite | ראה סעיף 3 |
| מיגרציות | Alembic | שינוי סכימה בלי לאבד נתונים |
| פרסינג | pandas + openpyxl | קובצי הבנק והאשראי |
| כספים | `Decimal` בלבד | אף פעם לא `float` — דיוק אגורות |
| סוכן | Agno (אופציונלי) | סיווג בתי עסק שלא נתפסו בחוקים |

### אריזה

Vite בונה לקבצים סטטיים, ו‑FastAPI מגיש אותם. **תהליך אחד, קונטיינר אחד, פורט
אחד** — בלי שני שרתים בפרודקשן. בפיתוח: `vite dev` על 5173 עם proxy של `/api`
ל‑uvicorn על 8000.

**למה לא Next.js:** אין צורך ב‑SSR או ב‑SEO באפליקציה פרטית של משק בית, וזה היה
מוסיף ריצת Node בפרודקשן לצד Python. אם בעתיד תרצה אתר שיווקי או SSR, המעבר
מ‑SPA ל‑Next הוא שכבת ניתוב חדשה מעל אותם רכיבים.

## 3. איפה נשמרים הנתונים

**ברירת מחדל: SQLite מקומי.** קובץ יחיד `data/household.db`, נתיב דרך
`HOUSEHOLD_DB_URL` ב‑`.env`, והתיקייה `data/` ב‑`.gitignore`.
נתונים פיננסיים לא נכנסים ל‑git, אף פעם.

למה SQLite:

- משפחה = משתמש בודד עד ספורים; אין צורך בשרת DB.
- אפס תחזוקה, עובד אופליין, גיבוי = העתקת קובץ אחד.
- הגישה עוברת דרך SQLAlchemy, ולכן מעבר ל‑Postgres בעתיד הוא שינוי של
  מחרוזת חיבור, לא כתיבה מחדש.

בנוסף נשמר: **קובץ המקור** שיובא, תחת `data/imports/<sha256>.xlsx`, כדי לאפשר
ייבוא חוזר ודיבוג של פרסרים.

### אזהרת פריסה

הריפו הזה נפרס כ‑Docker ל‑HuggingFace Spaces, ושם מערכת הקבצים **נמחקת בכל
restart**. לכן:

- **הרצה מקומית / NAS / מכונה שלך** → SQLite, ללא auth. זו ההמלצה ל‑v1.
- **אירוח בענן** → נדרש Postgres מנוהל (Neon / Supabase — יש free tier) **וגם**
  שכבת התחברות. מוסיף עבודה משמעותית, ולכן נדחה מ‑v1.

כדי שהמעבר לא ידרוש כתיבה מחדש, **כל טבלה נושאת `household_id` כבר מהיום הראשון**,
גם כשיש רק משק בית אחד.

## 4. מודל הנתונים

```
household        (id, name, currency, created_at)

account          (id, household_id, name,
                  type: bank | credit_card,
                  issuer, last4)

import_batch     (id, account_id, file_sha256, source_format,
                  rows_total, rows_inserted, rows_duplicate, imported_at)

category         (id, household_id, name, parent_id,
                  kind: fixed | variable | income | transfer)

category_rule    (id, household_id, pattern, match_type: contains | regex,
                  category_id, priority, created_by: user | llm | seed)

recurring_series (id, household_id, label, category_id,
                  cadence: monthly | bimonthly | quarterly | yearly,
                  expected_amount, tolerance_pct,
                  source: declared | detected, is_active)

transaction      (id, household_id, account_id, batch_id,
                  txn_date,           -- תאריך העסקה
                  billing_month,      -- חודש החיוב בפועל, מפתח הדיווח
                  amount NUMERIC,     -- שלילי = הוצאה, חיובי = הכנסה/זיכוי
                  currency,
                  merchant_raw, merchant_norm, description,
                  category_id, recurring_series_id,
                  is_transfer BOOL,   -- העברה פנימית, לא הוצאה
                  is_excluded BOOL,   -- החרגה ידנית של המשתמש
                  installment_no, installment_total,
                  row_hash UNIQUE)    -- מניעת כפילויות בייבוא חוזר
```

הסיכומים מחושבים ב‑SQL בזמן אמת. הנפחים קטנים (אלפי שורות לשנה), אין צורך
בטבלת סיכומים מראש.

## 5. צינור הייבוא

```
קובץ → זיהוי פורמט → פרסינג לשורות גולמיות → ולידציית Pydantic
     → נורמליזציה (סכום, תאריך, שם בית עסק) → row_hash → דה‑דופליקציה
     → סימון העברות פנימיות → קטגוריזציה → כתיבה ל‑DB → דוח ייבוא
```

- **זיהוי פורמט**: לכל פרסר יש `detect(df) -> bool` שבודק את כותרות העמודות.
  רישום הפרסרים ב‑registry; להוסיף בנק חדש = קובץ אחד חדש, בלי לגעת בליבה.
- **`row_hash`** = hash של (חשבון, תאריך, סכום, תיאור מקורי). ייבוא של אותו קובץ
  פעמיים לא יוצר כפילויות; ייבוא של קובץ חופף חלקית מוסיף רק את החדש.
- **דוח ייבוא** למשתמש: "נוספו 142 תנועות, 18 כפולות דולגו, 3 שורות לא נקראו".

## 6. הבעיה המרכזית: ספירה כפולה בין הבנק לויזה

קובץ הבנק כולל שורה אחת מרוכזת — `חיוב כרטיס אשראי 8,400 ₪-` — ואילו קובץ הויזה
כולל את אותן עסקאות בפירוט. סכימה נאיבית של שני הקבצים מנפחת את ההוצאות פי כמעט 2.

**הפתרון:** קובץ הויזה הוא **מקור האמת לפירוט**, וקובץ הבנק הוא **מקור האמת
להוראות קבע ולתנועות שאינן אשראי**.

1. שורות בבנק שמזוהות כ**סליקת כרטיס אשראי** (לפי תבנית תיאור + התאמה לסכום
   הכולל של מחזור החיוב בקובץ הויזה) מסומנות `is_transfer=true` ומוחרגות מהסיכום.
2. אם קיים חיוב אשראי בבנק שאין לו קובץ ויזה תואם (כרטיס שהמשתמש לא ייבא),
   השורה **נשארת כהוצאה** בקטגוריה "אשראי — ללא פירוט", והמשתמש מקבל התראה.
   כך אף שקל לא נעלם מהסיכום.
3. העברות בין חשבונות של אותו משק בית מסומנות אף הן `is_transfer=true`.

לוח הבקרה מציג מונה שקיפות: "מתוך חיוב אשראי של 8,400 ₪, 8,400 ₪ מפורטים".

## 7. חודש חיוב, תשלומים ומטבע חוץ

- **חודש חיוב מול חודש עסקה**: עסקה מה‑28/1 מחויבת ב‑10/2. כל הדוחות עובדים לפי
  `billing_month`, עם מתג בממשק למעבר לתצוגה לפי `txn_date`.
- **תשלומים** (תשלום 3 מתוך 12): כל תשלום הוא שורה בחודש החיוב שלו, עם
  `installment_no` / `installment_total` לתצוגה.
- **מט"ח**: נשמר הסכום בשקלים כפי שחויב בפועל, והמטבע המקורי נשמר לתצוגה בלבד.
- **זיכויים והחזרים** נשמרים כסכום חיובי ומקזזים את הקטגוריה בחודש שלהם.

## 8. הוצאות קבועות חוזרות

שני מסלולים משלימים:

**מוצהר** — המשתמש מגדיר ידנית: משכנתא 6,200 ₪ לחודש, גן 2,100 ₪. עובד גם בלי
שום קובץ מיובא, ומשמש כבסיס להשוואה מול המצב בפועל.

**מזוהה אוטומטית** — על בסיס ההיסטוריה המיובאת:

- נורמליזציה של שם בית העסק (הסרת מספרי אסמכתא, רווחים, סניפים).
- סף: לפחות 3 הופעות, מרווח עקבי, סטיית סכום מתחת לסף.
- קצב: 28–35 יום = חודשי, 55–70 יום = **דו‑חודשי**, וכן רבעוני ושנתי.
- ההצעה מוצגת לאישור המשתמש; אישור או דחייה נשמרים ולא מוצעים שוב.

### נרמול דו‑חודשי — קריטי לישראל

חשמל, מים וארנונה מגיעים לרוב **כל חודשיים**. בלי נרמול, גרף החודשים נראה כמו
מסור והממוצע מטעה. לכן יש שתי תצוגות:

- **תזרים בפועל** — מה באמת ירד מהחשבון בכל חודש.
- **עלות חודשית מנורמלת** — חשבון דו‑חודשי מחולק ל‑2, שנתי ל‑12.

**הממוצע החודשי וה"עלות הקבועה החודשית" מחושבים מהתצוגה המנורמלת.**

## 9. חישובים ומדדים

- סה"כ הוצאות לחודש נבחר.
- פילוח **קבוע מול משתנה** לאותו חודש.
- טבלת צולבת: קטגוריות × 12 חודשים אחרונים.
- **ממוצע חודשי** — על פני 12 החודשים המלאים האחרונים; החודש הנוכחי החלקי
  מוחרג מהחישוב כדי לא להטות אותו כלפי מטה.
- **בסיס קבוע חודשי** — סכום כל ה‑`recurring_series` הפעילות, מנורמל.
- **חריגות** — הוצאה קבועה שסטתה מהצפוי מעבר לסף ("חשמל גבוה ב‑32% מהממוצע").
- כל המדדים מוחרגים מ‑`is_transfer` ומ‑`is_excluded`.

## 10. קטגוריזציה

סדר העדיפויות, מהזול ליקר:

1. **חוקי משתמש** (`category_rule`) — התאמת מחרוזת או regex על שם בית העסק.
2. **חוקי ברירת מחדל** (seed) — רשימה מובנית של רשתות ובתי עסק נפוצים בישראל.
3. **סוכן Agno** — רק לבתי עסק שלא נתפסו, בקריאה מרוכזת (batch). התוצאה נכתבת
   כ‑`category_rule` חדש, כך שאותו בית עסק לא נשלח ל‑LLM פעמיים.
4. **ידני** — המשתמש משנה בטבלה; השינוי הופך אוטומטית לחוק.

ללא מפתח OpenAI האפליקציה עובדת במלואה — פשוט יותר שורות ב"לא מסווג".

**פרטיות:** ל‑LLM נשלח **רק שם בית העסק**. לא סכומים, לא תאריכים, לא מספרי חשבון.

## 11. הממשק

### RTL ועברית מהיסוד

- `dir="rtl"` על השורש, ו**תכונות לוגיות בלבד** ב‑CSS (`ms-*`/`me-*`, `ps-*`/`pe-*`)
  — אף פעם לא `left`/`right`. כך מעבר לאנגלית הוא החלפת `dir`, לא שכתוב.
- גופנים: Heebo / Assistant, עם ספרות שמתיישרות בטבלאות (`tabular-nums`).
- מספרים ותאריכים דרך `Intl.NumberFormat('he-IL', { currency: 'ILS' })` — לא פורמוט ידני.
- **בגרפים ציר החודשים זורם מימין לשמאל**, כמו קריאה בעברית.

### שפת עיצוב

מצב בהיר וכהה, כאשר **הכהה נבחר בנפרד** ולא היפוך אוטומטי של הבהיר. טקסט לובש
תמיד צבעי טקסט (ראשי / משני / עמום) ולעולם לא את צבע הסדרה — סימן צבעוני קטן
לצידו נושא את הזהות.

### מסכים

| מסך | תוכן |
|---|---|
| **ייבוא** | אזור גרירה, התקדמות לכל קובץ, תג של הפורמט שזוהה, תצוגה מקדימה, דוח "נוספו 142 · 18 כפולות · 3 שגיאות" |
| **עסקאות** | טבלה וירטואלית: עריכת קטגוריה בתוך השורה עם השלמה אוטומטית, בחירה מרובה לסיווג המוני, שורת סינון, תצוגות שמורות, עדכון אופטימי עם ביטול, ניווט מקלדת, ייצוא CSV |
| **דשבורד** | אריחי מדד + הגרפים שבמפרט למטה |
| **הוצאות קבועות** | כרטיס לכל סדרה עם sparkline של 12 חודשים, צפוי מול בפועל, תג חריגה, אישור או דחייה של סדרות שזוהו אוטומטית |
| **הגדרות** | עץ קטגוריות, חוקים עם תצוגה חיה של "תואם ל‑37 עסקאות", חשבונות, גיבוי |

חוצה־מסכים: לוח פקודות (Cmd+K), שלדי טעינה, מצבי־ריק שמלמדים מה לעשות, טוסטים
עם ביטול, ורספונסיביות עד רוחב טלפון.

### מפרט הגרפים

הצורה נגזרת מהתפקיד של הנתון, לא מהיופי:

| מה מציגים | צורה | למה |
|---|---|---|
| סה"כ החודש · ממוצע חודשי · בסיס קבוע | **אריח מדד** (מספר גיבור) + sparkline | מספר בודד הוא לא גרף |
| מגמת 12 חודשים | **עמודות**, קצוות מעוגלים 4px על קו הבסיס | חודשים הם קטגוריות בדידות |
| קבוע מול משתנה | אותן עמודות, **מוערמות**, 2px רווח בין המקטעים | יחס בתוך שלם, לאורך זמן — לא עוגה |
| קטגוריות × חודשים | **טבלת חום**, גוון אחד בהיר→כהה, **והמספר בכל תא** | צבע לבדו לעולם לא נושא ערך |
| קטגוריות בחודש נבחר | עמודות אופקיות, ממוין יורד, 8 מובילות + "אחר" | שמות ארוכים בעברית |
| חריגות | צבעי סטטוס + אייקון + מילה | סטטוס לעולם לא בצבע בלבד |

כללים שאינם ניתנים למשא ומתן:

- **ציר Y אחד. לעולם לא שני צירים.** הממוצע החודשי מוצג כקו ייחוס על אותו קנה מידה.
- צבע נצמד ל**ישות** ולא לדירוג — סינון שמשנה את מספר הקטגוריות לא צובע מחדש את הנותרות.
- מקרא לכל גרף עם 2+ סדרות, ותיוג ישיר כשיש עד 4.
- לוח הצבעים **נבדק בכלי אימות** (בהיר וכהה בנפרד) לפני שילוח — לא באומדן עין.
- לכל גרף יש **תצוגת טבלה** מקבילה. באפליקציה פיננסית אנשים רוצים את המספר.

## 12. מבנה בקוד ו‑API

הכל תחת תיקייה אחת `budget/`, בלי שום תלות בקוד ה‑Stock Analyzer — חילוץ לריפו
נפרד בהמשך הוא העתקת תיקייה.

### חוזה ה‑API

```
POST   /api/imports                      העלאת קובץ → דוח ייבוא
GET    /api/transactions                 סינון לפי חודש/קטגוריה/חשבון/חיפוש, עם דפדוף
PATCH  /api/transactions/{id}            שינוי קטגוריה, החרגה, הערה
POST   /api/transactions/bulk-categorize סיווג המוני
GET    /api/reports/monthly              סדרות חודשיות, עם דגל normalized
GET    /api/reports/summary              סה"כ, ממוצע חודשי, בסיס קבוע
GET    /api/reports/pivot                קטגוריות × חודשים
GET    /api/recurring                    סדרות קבועות + הצעות לאישור
POST   /api/recurring/{id}/confirm       אישור או דחייה של סדרה שזוהתה
GET    /api/categories  ·  /api/rules  ·  /api/accounts
```

כל נקודות הקצה `async`, עם מודלי תגובה של Pydantic. סכימת OpenAPI מייצרת את
טיפוסי ה‑TypeScript, ולכן שינוי בשרת שובר קומפילציה בחזית — ולא מתגלה בזמן ריצה.

## 13. בדיקות

**שרת (pytest)** — פרסרים מול fixtures של קבצים מטושטשים; דה‑דופליקציה בייבוא
כפול וחופף; התאמת בנק↔ויזה כולל המקרה בלי קובץ תואם; זיהוי מחזוריות חודשית,
דו‑חודשית, וסדרה רועשת שאסור שתזוהה; אגרגציות כולל חודש חלקי ושורות מוחרגות;
נקודות הקצה עצמן דרך `httpx.AsyncClient`.

**חזית (Vitest + Testing Library)** — פורמוט מטבע ותאריך בעברית, לוגיקת הטבלה,
מצבי טעינה וריק, ורינדור הגרפים עם נתוני קצה (חודש ריק, ערך שלילי).

**מקצה לקצה (Playwright)** — המסלול המלא: ייבוא קובץ → סיווג עסקה → הופעת הסכום
בדשבורד. Playwright כבר תלות בריפו ו‑Chromium מותקן.

**אימות לוח הצבעים** — סקריפט הבדיקה רץ ב‑CI לבהיר ולכהה.

ללא קריאות רשת או LLM בבדיקות, בהתאם ל‑CLAUDE.md.

## 14. אבטחה ופרטיות

- `data/` ב‑`.gitignore`. אין קובצי בנק ואין DB ב‑git.

## 16. מפרט הפורמטים — מאומת מול קבצים אמיתיים

שני הפורמטים נבדקו על קבצים אמיתיים, וההתאמה ביניהם הורצה בפועל. הסכומים
והשמות אינם במסמך הזה בכוונה — הריפו ציבורי.

### 16.1 כרטיס אשראי — ייצוא `xlsx` של מקס

- **3 שורות פתיח** לפני הכותרת: סינון משתמשים, סינון כרטיסים, וחודש החיוב (`08/2026`).
- **שורת כותרת רביעית**, 16 עמודות.
- **עד 3 גיליונות**: `עסקאות במועד החיוב`, `עסקאות חו"ל ומט"ח`, `עסקאות בחיוב מיידי`.
  גיליון שלישי מופיע רק כשיש חיוב מיידי — הפרסר חייב לעבור על הגיליונות הקיימים.
- **שורת סיכום בסוף כל גיליון**: `סך הכל` ואז הסכום עם `₪` דבוק. משמשת
  כ**בקרת שפיות** על הפרסינג, לא כנתון.
- עמודות מפתח: `תאריך עסקה`, `שם בית העסק`, `קטגוריה`, `4 ספרות אחרונות`,
  `סוג עסקה`, `סכום חיוב`, `סכום עסקה מקורי`, `תאריך חיוב`, `הערות`, `שער המרה`.
- **מלכודות:**
  - `סכום עסקה מקורי` בעסקת תשלומים הוא **סך כל התשלומים**, לא התשלום הנוכחי.
    סכימה של העמודה הזו מנפחת את ההוצאות. הסכום הנכון הוא `סכום חיוב`.
  - שדה `הערות` נושא מידע מובנה: `תשלום 2 מתוך 3`, `הוראת קבע`, `למי: <שם>`.
  - `סוג עסקה` מבחין בין `רגילה`, `תשלומים`, `חיוב עסקות מיידי`, `חיוב חודשי` —
    ולזה יש השלכה ישירה על תאריך החיוב בבנק.
  - תאריכים כמחרוזות `dd-mm-yyyy`.
  - **חברת האשראי כבר מספקת קטגוריה** לכל עסקה. זו נקודת פתיחה מצוינת: רוב
    הסיווג מגיע בחינם, וה‑LLM נשאר לשוליים בלבד.

### 16.2 חשבון בנק — `PDF` של לאומי

הבנק מייצא **PDF, לא Excel**, וזה משנה את שכבת הייבוא:

- ה‑PDF מיוצר ב‑HTML‑to‑PDF, ולכן חילוץ טקסט מחזיר עברית **הפוכה** — גם סדר
  התווים בתוך כל מילה וגם סדר המילים בשורה.
- הפתרון: פרסינג **מבוסס מיקום** (`extract_words` עם קואורדינטות), מיון מימין
  לשמאל, והיפוך התווים בכל אסימון עברי. מספרים ותאריכים נשארים תקינים.
- **קיבוץ שורות לפי סובלנות ולא לפי דליים.** עיגול של `top` לדלי שובר שורה
  שחלק ממנה סטה בפיקסל, ומאבד את התיאור. סובלנות של ~3px מתקנת.
- עמודות: `תאריך`, `תאריך ערך`, `תיאור`, `אסמכתא`, `בחובה`, `בזכות`, `היתרה בש"ח`.
- **חובה מול זכות נקבע מהיתרה הרצה**, לא מהצבע או מהעמודה: השורות מסודרות
  מהחדש לישן, ולכן `יתרה_קודמת − סכום == יתרה_נוכחית` מוכיח חיוב, והכיוון ההפוך
  מוכיח זיכוי. בבדיקה על דף אמיתי השיטה אימתה **229 מתוך 230** תנועות.
  **שרשרת היתרה ממשיכה מעבר לגבול עמוד** — איפוס בכל עמוד שובר בדיוק את השורות
  הגדולות שיושבות על התפר.
- התיאור והאסמכתא נדבקים בחילוץ; 4 הספרות של הכרטיס הן סוף האסימון.

### 16.3 אימות ההתאמה בין המקורות

האלגוריתם מסעיף 6 הורץ על הקבצים: סכום שורות סליקת האשראי בבנק, מקובץ לפי
תאריך, מול סכום `סכום חיוב` בקובצי הכרטיס מקובץ לפי `תאריך חיוב`.

**התוצאה: התאמה מדויקת לאגורה על כל 25 תאריכי החיוב, פער 0.00 ₪.**

זה מאמת את הליבה: אפשר להחליף כל שורת סליקה בבנק בפירוט העסקאות שמאחוריה,
בלי לאבד שקל ובלי לספור כפול.

### 16.4 שלושה תיקונים שהאימות חשף

1. **דה‑דופליקציה לפי תוכן בלבד מוחקת עסקאות אמיתיות.** בקובץ אמיתי נמצאו שתי
   קניות זהות לגמרי — אותו בית עסק, אותו יום, אותו כרטיס, אותו סכום. הן שתי
   עסקאות, לא כפילות. **מפתח הדה‑דופליקציה חייב לכלול מונה מופעים בתוך הקובץ**:
   שתי שורות זהות באותו קובץ שתיהן נשמרות, אבל ייבוא חוזר של אותו קובץ עדיין
   לא מכפיל דבר.
2. **סדרה קבועה מזוהה לפי תיאור וסכום, לא לפי תיאור בלבד.** משכנתא אחת מופיעה
   כשתי שורות באותו תיאור בדיוק עם שני סכומים שונים (שני מסלולים). קיבוץ לפי
   תיאור מייצר "סדרה" מדומה עם סטייה עצומה. הפתרון: פילוח לאשכולות סכום בתוך
   כל תיאור.
3. **`הוראת קבע` בשדה ההערות הוא סימון ודאי.** אין צורך להסיק מחזוריות בהיסק
   סטטיסטי כשחברת האשראי כבר אמרה זאת. הזיהוי ההיוריסטי נשאר רק למה שלא מסומן.

### 16.5 ממצא שמשנה את התכנון

**חשבונות חשמל, מים וארנונה לא מופיעים בדף הבנק כלל — הם משולמים בכרטיס
האשראי כהוראת קבע.** ההנחה המקורית, שהוצאות הבית הקבועות יושבות בבנק, שגויה
עבור הפורמט הזה. המשמעות: **קובץ האשראי הוא מקור האמת גם להוצאות הקבועות**,
והבנק מספק את מה שלא עובר בכרטיס — משכנתא, ליסינג, ביטוחים וקופות.

זו בדיוק הסיבה שאפליקציה כזו לא יכולה להסתמך על מקור אחד.

## 17. מה נשאר להחליט

**מה נחשב הוצאה.** בדף הבנק יש תנועות חובה שאינן צריכה: הפקדה לחיסכון, קניית
ניירות ערך, העברות בין חשבונות עצמיים, ומשיכת מזומן. אם כולן ייספרו כהוצאה,
"סך ההוצאות החודשי" יהפוך לחסר משמעות. ההצעה:

| סוג | ברירת מחדל | נימוק |
|---|---|---|
| חיסכון והשקעה | **לא הוצאה** — קטגוריה נפרדת | כסף שעבר כיס, לא נצרך |
| קניית/מכירת ניירות ערך | **לא הוצאה** | תנועה בתיק |
| העברה לחשבון עצמי | **לא הוצאה** (`is_transfer`) | ספירה כפולה |
| העברה לאדם אחר | **הוצאה** | תשלום בפועל |
| משיכת מזומן | **הוצאה**, בקטגוריה "מזומן" | היעד אינו ידוע |
| החזר מס, ריבית זכות | **הכנסה** | |

כל שורה בטבלה ניתנת לשינוי בהגדרות, כי לכל משפחה ההגדרה שונה.

**תשלומים (קרדיט).** נתח משמעותי מההוצאה בקובץ שנבדק הוא עסקאות תשלומים. שתי
תצוגות אפשריות: לפי **תזרים** (מה ירד החודש) או לפי **התחייבות** (מלוא העסקה
בחודש הרכישה). ברירת המחדל תהיה תזרים, כי זו השאלה "כמה עלה לנו החודש", עם
מתג לתצוגה השנייה ועם תחזית של התשלומים שכבר ידועים לחודשים הבאים.
